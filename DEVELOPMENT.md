## Purpose and target

The tools give a **local AI model** (run with Ollama through [ollmcp](https://github.com/jonigl/mcp-client-for-ollama)) what it needs for AI-driven development of Python and JS/TS projects: understanding the code, editing files, running tests and reviewing changes. Web search and fetch come from the `web` toolset, which uses Ollama's hosted web search API.

Most design decisions follow from the target model being small and local:
- **Small context windows** (8k–32k tokens): every response must be limited in size, and the tool definitions themselves cost context on every request.
- **Weak at exact copying and escaping**: models copy `\n`, `\"` or `ä` escapes and line number prefixes literally, drop trailing whitespace and use placeholders such as `// ... existing code ...`.
- **Follow instructions in tool descriptions and responses** fairly well, so errors and limits always say what to do next.

## Current state

One MCP server with six toolsets and 19 tools (17 while no Ollama API key is set, as the `web` tools are then not served). Each toolset is a module of the `ollmcp_tools` package; all of them use `ollmcp_tools/common.py` and read one config file, and the outline, filesystem and search toolsets also use the parsers in `ollmcp_tools/parsing.py`. `python -m ollmcp_tools` (`__main__.py`) imports the enabled toolsets and serves their tools, except the disabled ones.

Configuration:
- `python -m ollmcp_tools init` (`init.py`) sets up a project from the templates in `ollmcp_tools/templates`: `.mcp.json` and the `.ollmcp-tools` folder with `tools-config.json`, `commands.json`, `instructions.md`, `.gitignore`, an empty `suggested-commands.json` and `context/`, the user config file if it is missing, and the project's backup folder. It never overwrites a file.
- `.mcp.json` has one entry, `dev`, which runs `python -m ollmcp_tools` and gives it `MCP_TOOLS_CONFIG`, the path of the tools config file (`.ollmcp-tools/tools-config.json`). It contains no paths of the tools themselves, so it is the same in every project. ollmcp names tools `<server key>.<tool>` (e.g. `dev.get_outline`), and since version 0.35 sends them to every provider, Ollama included, as `dev_get_outline`, so the model sees and writes the `_` names. The instructions template and the system prompt use the `_` names too.
- The tools config file holds the project's settings: `project_dir` (required), `forbidden_paths`, `allowed_paths`, `read_only_files`, `ignored_dirs`, `gitignore_path`, `max_output_chars`, `command_registry`, `command_suggestions`, `backup_folder`, `disabled_toolsets`, `disabled_tools`. It is committed with the project.
- The user config file, `~/.ollmcp-tools/user-config.json`, holds each person's own settings for all their projects: only `ollama_api_key` so far.
- `ollmcp_tools/common.py` loads and validates the config and holds the shared helpers and constants, including `TOOLSETS`, the toolsets and their tools, which the two disabling settings are checked against before any toolset is imported.
- `pyproject.toml` makes the repository an installable package and lists its dependencies: `mcp`, `ollama` (for the `web` toolset) and `tree-sitter` with `tree-sitter-javascript` and `tree-sitter-typescript` (for JS/TS outlines). The tree-sitter packages are pinned to one minor version each, as the grammars must match the tree-sitter version. `requirements.txt` installs the `ollmcp` client and the package in editable mode (`-e .`); `requirements-dev.txt` includes it and adds the test runner.
- `ollmcp_tools/locations.py` holds the paths of the user's own folder of the tools: the user config file and the default backup folders (`default_backup_folder`). It reads no config, so both `common.py` and `init.py` use it.
- `ollmcp_tools/parsing.py` holds the Python, JS/TS and Markdown parsers and everything built on them: rendering outlines at a detail level, finding sections by name and comparing outlines before and after a write. It reads no config and no files.
- `ollmcp_tools/templates/` holds the files `init` copies. `commands.json` and `instructions.md` are examples for the user's projects, not development notes. This repository has its own `.ollmcp-tools`, created with `init`, with its own `commands.json` for pip and pytest; its `instructions.md` is a copy of the template.
- The instructions template starts by making the model choose a mode, answering, planning or implementing, and say it (`Mode: planning`), because qwen3-coder 30b started implementing when asked only for a plan while the instructions were a single implementation workflow (see [local_ai_test_results.md](local_ai_test_results.md#choosing-a-mode-2026-10)). Answering (questions, explanations, reviews) replies without writing any file, so a question does not leave a plan file behind; planning ends with a plan in `.ollmcp-tools/context`, written with `write_file`, a summary and questions to the user. Both list by name the tools they must not call, unclear requests never default to implementing, and only the user's request to change something or explicit go-ahead switches to implementing. The reading and search guidance is shared by all modes. Since 2026-10-23 the modes also say what gemma4 26b missed: the planning mode saves the plan with `dev_write_file` before the reply, a request to fix, add or change something is the permission to implement it, implementing starts by listing the plans with a concrete `dev_get_outline` call, and no reply ends by announcing a next step (see Model choice).
- The implementing mode is a concrete workflow for a small model (outline → section reads, which search to use when, hash-chained `edit_file`, `restore_file` after a broken write, API lookup, single tests before the suite or, in a project without test commands, the other listed checks and an honest report of what could not be verified, `get_git_diff` review, no commits) plus rules for limits, errors and web content. Small models follow concrete steps better than general advice such as "understand the project first". It is read into the context every session (about 2 000 tokens with gemma4 since the changes of 2026-10-23, 1 800 before), so keep it short. It cannot tell the model to read it at the start of a session, as the model only sees the file once it has read it: that instruction goes into ollmcp's system prompt and the user's first message of each session, which `init.py` prints as `SYSTEM_PROMPT` and `FIRST_MESSAGE` (see the README's [Starting a session](README.md#starting-a-session)).

## Principles applied

### Security model

- **`project_dir` is the boundary.** Every path given to a tool is resolved against it (relative paths too) and must stay inside it, except read-only files. Commands also run in it.
- **`forbidden_paths`** (relative to `project_dir`) are denied and hidden by every file-accessing toolset: filesystem, outline, search and git (through `:(top,exclude)` pathspecs, so a file's history cannot reveal its contents). Deleting or moving a folder that contains a forbidden path is denied.
- **`allowed_paths`** (relative to `project_dir`) inside forbidden folders can be used again with full access, and **`read_only_files`** can be read anywhere but never changed (see Allowed paths and read-only files).
- **Protected files** are always denied, regardless of the config: files named `.mcp.json` at any depth, the tools config file in use, the user config file and the `command_registry` (`PROTECTED_PATHS`), also before the registry exists. Otherwise the AI could remove its own restrictions or register any command, which would take effect at the next server start. The name check covers Windows aliases of the same file: letter case, trailing dots or spaces, `::$DATA` streams, 8.3 short names and symlinks.
- **The `commands` toolset** runs registered templates without a shell. The AI's argument is always one argument; arguments starting with `-` or containing line breaks are rejected, and for `.bat`/`.cmd` programs (e.g. `npm` on Windows) also `& | < > ^ % ! " ( )`. Commands get no input (prompts end immediately), have a timeout and succeed only with exit code 0.
- **Only the user adds commands.** `suggest_command` validates a suggestion with the registry's own checks (`_command_problem`) and writes it to the `command_suggestions` file, never to the registry; the user reviews the exact template and copies it over. A tool-call confirmation in the client was not used as the boundary: the server cannot rely on it, and an approval prompt is easy to click through. The server writes the entry with `json.dumps`, as small models get JSON escaping wrong (`\"`, Windows backslashes), and saving it to a file means the user copies the server's text, not the model's retelling. Shells and `-c`-style options together with `{arg}` are warned about, not refused, as a fixed `python -c "..."` can be legitimate.
- **Known limit, documented in the README:** commands execute project code that the AI can write, so they can read or change any file. Complete protection requires keeping `.mcp.json`, the tools config, this repository and the command registry outside the project folder (`ollmcp --servers-json <path>`).
- **The `web` toolset** only calls Ollama's hosted API (ollama.com), with the key from `ollama_api_key` in the user config file; it is passed to the `ollama` client explicitly, so the library's own `OLLAMA_API_KEY` environment variable is not used. `get_tools_config` only reports whether the key is set. Without a key the toolset is not served at all (`UNAVAILABLE_TOOLSETS` in `common.py`, shown as `not_served` by `get_tools_config`): the tools could only return `not_configured`, and their definitions cost about 900 characters of context on every request. This is the one exception to failing at startup, as a missing key is a normal choice, not a configuration mistake; only a config where `web` is the only enabled toolset stops the server. `web_fetch` accepts only `http(s)` URLs, and the page is fetched by Ollama's service, not locally. Web content can contain prompt injection; this is not filtered.
- **The backup folder of `restore_file`** is denied and hidden like a protected file (`is_backup` in `common.py`), even if `backup_folder` points inside the project, and a folder containing it cannot be moved or deleted. Otherwise the AI could change or delete the backups that are meant to undo its mistakes. A `backup_folder` containing `project_dir` stops the server at startup, as it would hide the whole project.
- **Ignored folders are not a security measure**: they only keep noise out of the outline and search tools.

### One configuration, strictly validated

- **Config files only.** The tools read no environment variables except `MCP_TOOLS_CONFIG`, apart from the home folder (`Path.home()`) for the user config file and the default backup folder of `restore_file`. There is deliberately no fallback to the old per-server variables (`ALLOWED_DIR`, `INPUT_DIR`, `FORBIDDEN_PATHS`, `MAX_OUTPUT_CHARS`, `GITIGNORE_PATH`, `COMMANDS_CONFIG`, `CONTEXT_FOLDER_PATH`, `READ_ONLY_FILES`, `PROJECT_INSTRUCTIONS_FILE`): one source guarantees that all toolsets see the same settings.
- **Fail at startup instead of silently degrading.** The server refuses to start if the config is missing or invalid JSON, has an unknown key (typo protection), lacks `project_dir` or points it to a missing folder, has a `backup_folder` that contains `project_dir`, has an allowed path outside every forbidden folder or outside `project_dir`, or one that is a protected file or the backup folder, has a read-only file that does not exist or is protected, has a value of the wrong type, names an unknown toolset or tool in `disabled_toolsets` or `disabled_tools`, or disables every tool. A renamed or moved setting (`MOVED_SETTINGS`: `commands_config`, `ollama_api_key`) gets an error that says what to do instead, and a missing `project_dir` folder or read-only file an error that says what the path was resolved against. Settings and tools removed without a replacement, such as `context_folder`, `allowed_dir` and `create_file`, get the plain unknown-name error: there is no backwards compatibility yet. The user config file is checked the same way (invalid JSON, unknown setting, a key that is not a string). The same applies, while their toolsets are enabled, to the command registry (missing file, invalid JSON, command without `template`/`description`, invalid `timeout`, a placeholder other than `{arg}` such as `{args}`, which would otherwise be passed to the program as literal text).
- **`project_dir` is relative to the config file's folder, and every other path in the config is relative to `project_dir`** (since 2026-10-20). Paths are then written as the AI writes them (`.ollmcp-tools/instructions.md`), and one rule covers the whole file. Before, all paths except `forbidden_paths` and `allowed_paths` were relative to the config file, so that a config moved outside the project only needed a new `project_dir`; now its registry, suggestions file and read-only files need new paths too, which the README explains. That setup is rare, and a wrong registry or read-only file stops the server.
- **`null` means "use the default"** for every optional setting, so a config can list a setting without using it. An empty list is different: `"ignored_dirs": []` skips nothing, while `null` uses the defaults.
- **Project-specific values belong in the config; code only holds defaults** (e.g. `DEFAULT_IGNORED_DIRS`). A given `ignored_dirs` list replaces the defaults completely, so that a default such as `build` can be un-ignored. Entries are folder names, not paths.
- **One config tool**: `get_tools_config` in the `filesystem` toolset (the most essential one) reports the settings, the enabled toolsets and disabled tools, and what each toolset sees. Other toolsets point to it ("Use get_tools_config to see why") instead of having their own config tools.

### One server, toolsets chosen in the config

- **Seven servers in `.mcp.json` were hard to set up.** Each needed the absolute path of its script for use in another project, and a path containing a non-ASCII character, such as `ä` in a Windows user name, broke the server loading unless it was written as `\u00e4`. The tools are now an installed package started with `python -m ollmcp_tools`, so `.mcp.json` names a module instead of a path and is the same in every project. The package is installed in editable mode, so a `git pull` updates every project.
- **One server key, `dev`.** With seven keys, a small model can pair a tool with the wrong prefix (`filesystem.get_outline`); with one there is only one way to write a name, and the instructions file is shorter.
- **Tools are named by their context**, as the server key no longer gives it: `get_git_diff`, `get_git_history` (it also covers folders, so not `get_git_file_history`) and `get_tools_config` instead of `get_diff`, `get_file_history` and `get_config`. The other names already said what they work on (`search_*`, `web_*`, `run_predefined_command`).
- **Disabling instead of enabling**: `disabled_toolsets` and `disabled_tools` default to nothing, so the default config has every tool, like the separate servers had. Names are checked against `TOOLSETS` in `common.py`, so a typo stops the server instead of leaving a tool enabled. A toolset added later is enabled unless the user disables it.
- **A disabled toolset is not imported**, so its own startup checks (e.g. a missing command registry) do not run. A toolset whose tools are all disabled is treated the same way.
- **Each toolset module still defines its tools on its own `MCPServer`** (`mcp = MCPServer("<toolset>")`), which only holds them: `__main__.py` takes the tools from the enabled toolsets' tool managers and creates the served `MCPServer` with them. This kept the tool definitions unchanged; the toolsets cannot be started on their own.
- **Trade-offs**: an invalid setting of any enabled toolset stops all of them, which fits "fail at startup"; ollmcp's tool menu shows one group instead of seven; and a long tool call, such as a command running up to its timeout, blocks the other tools, which does not matter as ollmcp calls tools one at a time.

### Setting up a project

- **One folder per project, `.ollmcp-tools`**, named after the package rather than ollmcp, as ollmcp itself does not read it. `project_dir` is relative to the config file, so the template's is `".."`; the README, the `init` checklist and the startup error for a missing folder explain it, as JSON has no comments.
- **`forbidden_paths: [".ollmcp-tools"]` in the template** hides the whole folder from the file, outline, search and git tools, with two exceptions: `allowed_paths: [".ollmcp-tools/context"]` gives the AI its plans folder, and `read_only_files: ["instructions.md"]` lets it read the instructions. The commands toolset reads the registry directly, so it still works. Forbidding the folder and allowing parts of it was chosen over not forbidding it and protecting its files by role (the config and registry are protected already; the suggestions file and instructions could be read-only): that is simpler, but a file added to the folder later would be visible by default.
- **Committed: the config, the registry and the instructions**, which are the same for everyone working on the project, and `forbidden_paths` is a security setting that every person must get. Ignoring them and having everyone run `init` was considered and rejected: `init` only gives the generic templates, so each person would rebuild the project's commands, and someone would miss a forbidden path without noticing.
- **Not committed: `context/` and `suggested-commands.json`** (the folder's own `.gitignore`, so the project's `.gitignore` is not edited). Plans belong to one person's current task, and the instructions tell the AI to check the existing plans first, so a shared stale plan would mislead another person's AI.
- **The API key is in the user config file**, as it belongs to a person, not a project, and a key in a committed config would leak. An `ollama_api_key` in the tools config stops the server.
- **One folder per user, `~/.ollmcp-tools`**, holds the user config file and, in `backups/`, the default backup folders of `restore_file` (`USER_FOLDER` in `locations.py`), so the tools add a single folder to the home folder.
- **The commands template uses pip and `python -m`** (`python -m pytest`, `python -m ruff`, `python -m mypy`), which work in any Python project with a `requirements.txt`. Running the tools as modules finds them in the same Python environment as the packages. The template had poetry commands before, which came from one project and did not suit a default; pip has no development-only group, so `add_dev_package` was dropped, and `add_package`/`remove_package` tell the AI to update `requirements.txt` too, as pip records nothing. `remove_package` needs `--yes`, as commands get no input.
- **The server and the commands use the `python` found on PATH when ollmcp starts.** For a project's virtual environment, the user starts ollmcp in the activated environment and installs the tools into it too. Writing the environment's Python as an absolute path into `.mcp.json` was rejected, as `.mcp.json` would then contain a path again and differ between machines.
- **`init` never overwrites**, so it is safe to run again; after cloning, it only creates what each person keeps for themselves: the context folder, the suggestions file, the user config file and the backup folder. The allowed context folder does not have to exist for the server to start, as the AI creates it with its first plan. `init` does not import `common.py`, as there is no config to load yet; both use `locations.py`, and `init` reads `project_dir` and `backup_folder` from the created config to find the backup folder the server will use.
- **`init` creates the empty `suggested-commands.json` and the backup folder** (decided 2026-10-20), so that the user sees where the AI's suggestions and the backups of changed and deleted files go before the first one exists. The suggestions file stays gitignored, so `init` recreates it after cloning. Moving the backups into `.ollmcp-tools` to make them visible in the project was rejected: they would then be inside the project, where the commands the AI runs can reach them, and a deleted large folder would be copied into the project; they stay in `~/.ollmcp-tools/backups`, and `init` prints the folder. If `project_dir` or `backup_folder` is changed afterwards, the created folder stays empty and the server creates the new one.
- **Settings that depend on each person's model** (`max_output_chars`, `disabled_tools`) are in the committed config for now. A `tools-config.local.json` that overrides single settings and is not committed is a possible later addition.

### Output limits

- `max_output_chars` (default 40 000 characters, about 10 000 tokens, minimum 2 000) limits every response. Tool-specific limits sit on top: 1000 lines per read, lines over 2000 characters shortened, 100 search matches, 30 files with 3 lines each for `search_relevant_files`, 200 listed changed files, files over 1 MB not outlined, folders with over 1000 files outlined by subfolder only, outlines after writes up to `min(2500, max_output_chars // 8)` characters, text files over 50 MB not read.
- **A limited response always contains `Output limited:`** (in JSON: an `output_limited` field) saying what was left out and the exact next call: which `start_line` to read next, which subfolders to outline with `path` (with file counts, descending into a folder that holds everything), which `path` has the most search matches, a smaller history `limit`, a narrower command.
- Room for the notes scales with the budget (`min(X, max_output_chars // 4)`), and text inside JSON uses 90 % of its budget to leave room for escaping.
- The instructions template tells the AI to follow these messages instead of repeating the call and never to assume a limited response is complete.
- Command output keeps the start and the end (errors are usually at the end); diffs and files keep the start.

### Outlines and section reads instead of cut-off content

- **Outline first, then read only what is needed.** `get_outline` returns files with their sections (classes, methods, functions, components, types, headings) and the line span of each section; the AI then reads one section with `read_file_with_metadata(path, section=...)` or `start_line`/`end_line`. This replaced `generate_codebase_map`, which described files in walk order until the output limit and dropped the rest, and `generate_file_map`, which only listed the map's file types.
- **Reduce detail instead of cutting.** A folder outline that does not fit drops, in order: summaries, sections below the top level, all sections (files with section counts remain), and finally files in subfolders (subfolders with file counts remain). Every level still covers the whole folder, and the response names the level and suggests subfolders. Folders with more than 1000 files go straight to the last level without reading the files. A single file's outline drops calls, then summaries, then nested sections, and is only cut short as a last resort.
- **Full relative paths instead of a tree with connectors**, so that a path can be copied into the other tools as-is.
- **Reading by name** (`section`), because small models copy line numbers wrongly and line numbers go stale after an edit, while a name resolves against the current file. A name matches the full name (`App.run`, `Guide > Install`) or the name alone, first exactly and then ignoring letter case; an outline line copied as the name (`18-60 class App`, `## Install`, `run()`, even a whole line such as `class App extends Base (export): Summary`) also works, but only if the name as given matches nothing, so that a heading such as `type checking` is not also found as `checking`. Several matches return the candidates with their spans instead of guessing; if they have the same full name, the error points to `start_line` and `end_line`.
- **Outline after every write** to a Python, JS/TS or Markdown file (`edit_file`, `write_file`, `restore_file`), with the sections removed and added compared to the outline before the write. An explicit "no longer in the file" warning is more reliable than expecting a small model to notice a missing entry. A Python file that parsed before but not after the write is also warned about, which catches broken indentation early, and so is a new JS/TS syntax error (only a new one, so that syntax the grammar does not know is not reported after every write). Blocks of top-level statements are not compared, as their names change with every new constant.
- **Spans**: Python from the first decorator to `end_lineno`, top-level statements between definitions grouped as blocks (`docstring, imports, assignments: A, B`); JS/TS from the JSDoc (and decorators) to the end of the declaration's syntax tree node, overloads and getter/setter pairs spanning all their declarations; Markdown from the heading to the line before the next heading of the same or a higher level, without trailing blank lines, skipping code blocks and front matter.
- The parsers are in their own module, `parsing.py`, which reads no config and no files.
- **JS/TS outlines** list functions, components, hooks, classes with methods, interfaces, types, enums, exported constants, default/named/CommonJS exports, re-exports, local imports and JSDoc summaries. They include namespaces and modules (`namespace N {}`, `declare module "x" {}`, `declare global {}`) with their contents, and every form of default export (`export default` of any value, `export = f`, `export { a as default }`, `module.exports = function/class/name`). Overloads, and getter/setter pairs, form one section only when declared one after the other.
- **JS/TS uses tree-sitter** (`tree-sitter`, `tree-sitter-javascript`, `tree-sitter-typescript`), which replaced a regex parser in 2026-09. The regex parser needed a special case for every construct (type arguments, object return types, apostrophes in JSX text, regex literals, statements continued on the next line) and kept producing wrong spans, which matter now that section reads and the outline after writes depend on them. `.ts` files use the TypeScript grammar, `.tsx` its TSX variant and other files the JavaScript grammar, which includes JSX. tree-sitter also outlines files with syntax errors and reports the first one (`Outline.syntax_error`).

### Responses in the console

- **ollmcp renders a non-JSON response as Markdown when it counts more than 7 Markdown-like patterns** (backticks, `#` lines, list markers, `*`), and otherwise as plain text (`_count_markdown_patterns` in its `utils/tool_display.py`). File content almost always crossed that threshold, and Markdown then joined the header lines into one paragraph, turned `# comments` into headings and ran the `----- BEGIN CONTENT -----` markers into the text.
- **Text responses are therefore written for both modes** with `text_response()` and `code_block()` in `common.py`: header lines as a list, content and other line-based output (outlines, search matches, listings) in fenced code blocks with the file's language (`code_language()`), and blank lines between the parts. The list markers and fences count as Markdown patterns themselves, so in practice the responses are consistently rendered as Markdown. The fence is longer than any backtick run in the content.
- Models know code fences well; `edit_file` removes copied fence lines from `old_text` like copied line numbers. Short single-line responses (errors, `No files found matching pattern: ...`) stay plain sentences.

### Local-model-friendly reading and editing

- **`read_file_with_metadata` and `edit_file` return plain text**, not JSON: a short metadata header and the exact content in a fenced code block. JSON escaping made models copy `\n` and `\"` into `edit_file`. Errors of these two tools are `Error (<code>): <message>`. `web_fetch` uses the same format, as code is often copied from web pages.
- **`edit_file` tolerates common copying mistakes**: copied `N| ` line number prefixes and code block fence lines are removed, trailing whitespace does not need to match, and when nothing matches, the error shows the lines that match with different indentation so they can be copied exactly. Multiple matches are reported with their line numbers.
- **Hash-checked writes**: every edit needs the SHA-256 from the last read or edit, and the edit response shows the changed lines and the new hash, so edits can be chained without re-reading. `restore_file` also returns the new hash of a restored file.
- **Placeholder comments** (`// ... existing code ...`, `# rest of the code`, etc.) are rejected in `edit_file` and `write_file` unless the original already contains one. `write_file` warns if a file of 20+ lines shrinks below half.
- Line endings (LF/CRLF) and BOMs are preserved; writes are atomic.
- **JSON responses use `ensure_ascii=False`**, so `ä` stays readable instead of `\u00e4`. ollmcp 0.35 still shows JSON responses with `\u00e4` in the console, as its `_format_json` (`utils/tool_display.py`) formats them again with `json.dumps(data, indent=2)`; the model gets the response as the tool returned it.
- `read_image` returns a real MCP image (ollmcp forwards it to vision models) with the format detected from the file's bytes.

### Undo with restore_file

Small models break files, and the outline warnings after a write only help if the model can get the file back: rebuilding it from memory is what just went wrong. `restore_file` undoes the changes of the file tools one at a time, newest first.

- Every change is recorded in `journal.json` in the backup folder before it is made, with a copy of a changed file (`_record_change` in `filesystem.py`). `delete_file` moves the file or folder into the backup folder instead of removing it. If the backup fails, the change is not made (`backup_error`), so every change can be undone.
- A restore picks the latest change not restored yet to the path, to a folder containing it, or (for a move) to its old or new path, so changes are undone in reverse order also across moves and folder deletions. What a restore replaces is moved into the backup folder, never removed.
- Git was considered instead (`git restore`), and rejected: it goes back to the last commit, losing every uncommitted change instead of only the last one, has nothing for new or untracked files, cannot bring back a deleted untracked file, and would be a git write tool.
- The default backup folder is in the user's own folder of the tools, `~/.ollmcp-tools/backups`, one per project (`<name>-<hash of the path>`), so backups are not in git or the project. `get_tools_config` reports it. The tests point the home folder to their temporary folder (`_use_temporary_home` in `conftest.py`).
- The instructions template tells the AI to undo a change that broke a file with `restore_file` instead of rewriting the lost parts from memory, and `delete_file` says in its response how to undo the deletion.

### Allowed paths and read-only files

Added on 2026-10-20, replacing the `context` toolset (4 tools, about 500 prompt tokens), which had its own folder and file name rules for the plans and the instructions. The file tools now handle both: `read_file_with_metadata` reads Markdown sections, `get_outline` lists headings, and every write shows the outline.
- **`allowed_paths`** are folders or files inside forbidden folders that the tools may use again with full access, e.g. `.ollmcp-tools/context` while `.ollmcp-tools` stays forbidden. The most specific path wins (`is_forbidden` compares the deepest forbidden and the deepest allowed path containing a path), so a forbidden path inside an allowed one is still forbidden. The server refuses to start if an allowed path is not strictly inside a forbidden folder (everything else is allowed already, so it is a typo or a needless setting), is outside `project_dir`, or is a protected file or in the backup folder.
- **`read_only_files`** are readable by the file, outline and search tools wherever they are, also inside a forbidden folder or outside `project_dir` (`is_path_readable`), and never writable (`_is_writable` in `filesystem.py`): `write_file`, `edit_file`, `delete_file` and `restore_file` are refused, and `move_file` as source or destination; a folder containing one cannot be moved, deleted or restored (`contains_read_only`). They must exist at startup.
- **The AI must find read-only files outside `project_dir`** (the user's requirement): `get_outline` of the whole project lists them after the project's files, with their absolute paths and outlines, marked `read-only`, so that the AI can pass the path to `read_file_with_metadata`. Read-only files inside the project are listed in their place, also marked. The searches cover the project folder only, as their folder suggestions and paths assume it, but accept such a file as their `path`.
- **`.gitignore` and `ignored_dirs` do not hide allowed paths and read-only files.** The user gitignores the whole `.ollmcp-tools` and `.mcp.json` (to keep them from colleagues who do not use the tools), and the `context` toolset never applied `.gitignore`, so the plans would otherwise disappear. Inside an allowed path, only the part of a path below it is compared with them. A forbidden or ignored folder that contains an allowed path or read-only file is entered as a THROUGH folder that shows only those, and can itself be outlined or searched (`get_outline(".ollmcp-tools")`).
- **Git:** a git pathspec cannot include a path again after an exclude, so the git tools keep hiding the whole forbidden folder, allowed paths and read-only files included, and say so for such a path (`forbidden_folder`). Accepted by the user: it only costs the history of `instructions.md`, and their `.ollmcp-tools` is gitignored anyway.
- **`allowed_dir` was renamed to `project_dir`**, as `allowed_dir` next to `allowed_paths` read as if both did the same thing, while one is the project root and the other exceptions inside forbidden folders. A list of allowed folders replacing `allowed_dir` was considered and rejected: the tools need one root to resolve relative paths, show paths, run commands and outline the project, so a list would need a hidden "first entry is the root" rule, and a typo in it would silently allow a new folder. `root_dir` was rejected as it is easily mixed up with `repository_root` of `get_git_diff`.
- **Session start:** the system prompt is now *At the start of a session, call dev_read_file_with_metadata with path '.ollmcp-tools/instructions.md' and follow it.* When the first message is a task, the model often skips it, so the user starts each session by asking the AI to read the instructions (see Session start and plans).

### Outline and search

- Folders are skipped without being entered (`walk` in `common.py`), so a large `node_modules` costs nothing. Only the part of a path inside `project_dir` is compared with `ignored_dirs`, so a project inside a folder named e.g. `out` is not hidden. A hidden folder that contains an allowed path or a read-only file is entered, and shows only those (`visibility` in `common.py`).
- The outline and search tools respect `.gitignore` with a simplified matcher (no `!` negations; folders without a trailing `/` match at any depth). The repository's own `.gitignore` is written for that.
- `search_text_in_files` searches for a query that is not a valid regex (e.g. `functionName(`, which small models often search for) as literal text, and says so in a `Note:` line, instead of returning an error.
- `search_relevant_files` is for when the exact text is unknown: the model gives a sentence, code or an error message and gets the best files ranked, each with its best outline section and the call to read it. How it ranks:
  - Keywords are the words and identifiers of the query, each identifier also split into its parts (`getUserName` → `getusername`, `get`, `user`, `name`; `get_user_name` gives the same whole form, so both styles match each other). Keywords have at least 2 characters, numbers at least 3 digits. Files are matched by whole tokens, not substrings, so `id` does not match `width`.
  - Files are scored with BM25: a keyword found in few files weighs much more than one found in almost every file (inverse document frequency), repeats of a keyword add less and less, and long files are scored down. The score is scaled by the share of the query's keyword weight the file has, so a file with several rare keywords beats one with a single keyword repeated. A keyword in the file path adds its weight once.
  - The best section of a file is scored the same way by its own lines, without its subsections, so a document under a single `#` heading or a whole class does not win just by containing every match. Files without an outline are compared 30 lines at a time.
  - The top `3 × max_results` files are reranked with a bonus when their best section is named after a keyword, so the definition of a name ranks above files that only use it.
  - The response lists the keywords with their file counts and weights (0–1), the keywords not found anywhere (often a misspelled or invented name), and a note when all keywords are common.
  - The docstrings of `search_text_in_files` and `search_relevant_files` point to each other: every use of a name (e.g. before renaming it) comes from `search_text_in_files`, as `search_relevant_files` shows only the best files.
  - There is no index: every search reads the files again. Text that cannot contain a keyword is skipped with one regex check per line and identifier, which keeps a 2 800-file project (Python's standard library) at about 2 seconds.
- Outlines and text search can be limited to a folder with `path`. The outline of one Python file scans the whole project for Python symbols, so that "Calls:" works across folders; folder outlines do not show calls.

### Tool count

Every tool definition is sent with every request, so tools that duplicate others were removed: `get_file_stats` (covered by the read and the hash check), `is_git_repository` (`get_git_diff` returns `not_a_repository`), `instructions-mcp` (now `read_only_files`), `generate_codebase_map` and `generate_file_map` (now `get_outline`), `get_file_diff` and `get_all_changes_diff` (now `get_git_diff`), `read_all_context_files` and `append_to_context_file` (later the whole `context` toolset), `create_directory` (`write_file` and `move_file` create missing folders), the four per-server config tools (now `get_tools_config`) and `read_image_as_base64` (replaced by `read_image`). On 2026-10-20 followed `create_file` (now `write_file` with an empty `expected_sha256`), `get_git_status` (now `get_git_diff`), `list_directory` (covered by `get_outline` and `search_files_by_pattern`) and the `context` toolset (`list_context_files`, `read_context_file`, `write_context_file`, `remove_context_file`; covered by the file tools with `allowed_paths` and `read_only_files`), see below. A removed tool still named in `disabled_tools` stops the server like any unknown name. The tools a project does not need can also be left out with `disabled_toolsets` and `disabled_tools`.

The size of the definitions matters beyond the context it costs: with qwen3-coder 30b, broken tool calls (a call written as plain text, which never reaches the server) became more frequent as the definitions grew, and a system prompt that names the session start prevented most of them. The results, and how they were measured, are in [local_ai_test_results.md](local_ai_test_results.md#broken-tool-calls-2026-10-19). Two of them shape the code: qwen3-coder's prompt template does not show schema defaults, so the "Defaults to …" lines in the docstrings are the model's only source for them, and the docstring indentation cost about 90 tokens, so it is removed (see Code conventions). The README's [Starting a session](README.md#starting-a-session) gives users the prompt and the remedies (`num_ctx`, `/clear` after a broken call). gemma4 26b breaks differently: none of its first calls was broken, but in longer tasks it sometimes answers with only a token of its chat template (`<|tool_response>`) or leaves one in its answer (`<channel|>`), see [local_ai_test_results.md](local_ai_test_results.md#qwen3-coder-30b-and-gemma4-26b-compared-2026-10-23).

Decided on 2026-10-19 while reducing the definitions:
- **Docstring wording is not shortened.** The "Defaults to …" phrases are the model's only source for the defaults (see above), and the `Returns:` sections carry guidance such as reusing the new SHA-256. Only the indentation is removed, by `prepare_tools()` (done, see Code conventions).
- **`web_search` and `web_fetch` stay separate.** Merging them would save about 300 characters, and a small model fills in "either `query` or `url`" less reliably than two clear tools.
- **The `web` tools are left out without an API key** (done, see the security model).

Decided on 2026-10-20:
- **`create_file` is merged into `write_file`.** An empty `expected_sha256` creates a new file and any missing folders, with the line endings of the neighbouring files, as `create_file` did; a hash replaces an existing file. Both mistakes a merged tool makes possible are refused with `Nothing was changed.`: a hash for a missing file (`file_not_found`, usually a mistyped path, which would otherwise be created as a new file) and no hash for an existing file (`file_exists`, as `create_file` refused it). A created file is recorded for `restore_file` as a change by `write_file`.
- **`get_git_status` is merged into `get_git_diff`.** The diff of all changes already listed the changed and untracked files; it now also shows the branch, and `mode` defaults to `'head'` (staged and unstaged changes together), so `get_git_diff()` without arguments replaces the status. In a repository without commits, `'head'` compares with the empty tree (`_diff_args` in `git.py`), as `git diff HEAD` fails there. What `git status` showed and the diff does not: commits ahead of or behind the upstream branch and the note about a merge or rebase in progress (unmerged files are still listed with `U`). The AI does not commit, push or merge, so they were not needed.
- **`list_directory` is dropped.** `get_outline` of a folder lists every file with its line count, and `search_files_by_pattern` finds files by name; only file sizes and modification times are lost. `read_file_with_metadata` of a folder now points to `get_outline`.
- **The `context` toolset is removed** (see Allowed paths and read-only files). With the three tools above, the definitions went from 11 307 to 9 203 characters, and with qwen3-coder 30b from 4 109 to 3 327 prompt tokens with every tool (3 855 to 3 071 without the `web` tools; see [local_ai_test_results.md](local_ai_test_results.md#size-of-the-tool-definitions-2026-10-20)).
- **`read_image` stays enabled by default.** ollmcp does not reload the tools when the model is switched during a session, so a default based on the model would be wrong after a switch, e.g. from a vision model such as gemma4:26b to qwen3-coder. ollmcp skips the image for a model without vision and shows a warning. A user who only uses models without vision can add it to `disabled_tools`.

### Session start and plans

Decided on 2026-10-20, after replaying a reported session in which the model wrote a new plan with the name of an existing one (results in [local_ai_test_results.md](local_ai_test_results.md#session-start-and-plans-2026-10-20)):
- **The user starts each session by asking the AI to read the project instructions.** When the first message is already a task, qwen3-coder mostly skips the session-start system prompt (its first call read the instructions in 2 of 18 runs, and no rewording did better than 7 of 18), and without the instructions it even changed code when asked to change a plan. The system prompt stays: together with "Read the project instructions." as the first message, the first call read the instructions in 20 of 20 runs, and without it in 9 of 20. The user chose asking as the most transparent option. The README's [Starting a session](README.md#starting-a-session) and the `init` checklist (`FIRST_MESSAGE` in `init.py`) tell users to do both. Rejected: the server adding the instructions to its first tool response after each start (it cannot tell when `/clear` starts a new conversation, and the first call is made without them), and pasting the instructions into ollmcp's system prompt (ollmcp has one global configuration for all projects, and it would have to be updated by hand).
- **The instructions template was kept** (until the changes for gemma4 on 2026-10-23, see Model choice). With the instructions read, it handled the reported request in every run: the model tried `write_file` on the existing plan, got `file_exists`, and edited the plan, which is the error the user saw. Five rewrites that listed the plans first and said how to change an existing plan made the model update it less often, as it then gave the changed plan in its reply without saving it.
- ollmcp uses only its own system prompt, not the instructions an MCP server can send, so the server cannot give the model its instructions directly.
- **The same session start works for gemma4 26b** (measured on 2026-10-23): with the system prompt and "Read the project instructions.", its first call read the instructions in 10 of 10 runs, without the system prompt in 5 of 10, and with a task as the first message in 2 of 12.

### Model choice

Decided on 2026-10-23, after running qwen3-coder 30b and gemma4 26b on the same seven tasks, three times each, with the real tools (`local_ai_tests/compare_models.py`; results in [local_ai_test_results.md](local_ai_test_results.md#qwen3-coder-30b-and-gemma4-26b-compared-2026-10-23)):
- **gemma4 26b is the recommended model**, as it keeps the modes apart: it never changed code when asked for an answer or a plan, and it changed an existing plan correctly in every run. Its weaknesses are visible in its reply and cost the user one message: it reads less than it should, asks before a direct fix, and sometimes stops after announcing a step.
- **qwen3-coder 30b is not recommended**, although it reads more and verifies its changes better: in planning mode it went on to implement (2 of 3 runs of "What should we change?"), and it replied "I updated the plan" without changing the file (2 of 3). Those mistakes are silent, and the mode rules are what the instructions build on. The README's [Why not qwen3-coder](README.md#why-not-qwen3-coder) gives users the reasons. Its earlier results stay valid for qwen3-coder and are kept in local_ai_test_results.md.
- **The instructions template was changed for gemma4**, measured over three seeds per task before and after (see [local_ai_test_results.md](local_ai_test_results.md#instructions-for-gemma4-2026-10-23)): the planning mode names saving the plan with `dev_write_file` (new plans saved in 3 of 3 runs instead of 0 of 3), implementing has examples ("fix…", "add…", "change…") and says that such a request is the permission, its first step is a concrete `dev_get_outline` call on the plans folder, and replies must not end by announcing a next step. Rejected after measuring: a rule to read the functions in other files that the read code calls (no effect: gemma4 still read only one of the three files a question needed), naming the plan as needing no permission in the rule against changing files (direct fixes then went to planning in 3 of 3 runs), and saying that a fix needs no plan (no effect, as gemma4 chooses the planning mode before it reads the implementing steps).
- **Direct fixes are still gemma4's weak point**: asked "Fix the bug where…", it chose the planning mode and asked for permission in 2 of 3 runs with the changed instructions. The user then answers "yes", and implementing an approved plan passed the hidden tests in 3 of 3 runs.
- Both models were measured fully on the CPU, as the developer's 8 GB GPU holds neither; only one should be loaded at a time, as two loaded together ran the 64 GB machine low on memory.

### Code conventions

- Files start with `# --- file.py ---`, then stdlib imports, third-party imports (e.g. `ollama`, `tree_sitter`), then `from mcp.server.mcpserver import ...`, `from .common import (...)` and, if needed, `from .parsing import (...)`. Sections of a toolset: `Constants & Config` (`mcp = MCPServer("<toolset>")` first), `Internal Helpers`, `Public MCP Tools`.
- A new toolset is a module in `ollmcp_tools/`, added to `TOOLSETS` in `common.py` and to `EXPECTED_TOOLS` in `test_servers_start.py`; a new tool is added to both lists too. Tool names are unique across the toolsets, and say what they work on without the server key.
- Helpers are `_`-prefixed with short summary docstrings. Public names in `common.py` have no prefix.
- **Tool docstrings are sent to the model with every request**, so they are short: what the tool does and what the model must get right, then `Args:` with one short line per parameter (no types, which are in the schema) and `Returns:` only if the response is not obvious. Guidance that errors give when it is needed (e.g. read again after `hash_mismatch`) is not repeated in descriptions. Optional strings default to `""` instead of `None`, and `__main__.py` calls `prepare_tools()` from `common.py` on the served server. It removes the generated titles and `anyOf: [type, null]` from the schemas, and makes an argument sent as `null` use the parameter's default, as small models often send `null` for optional parameters (`test_null_arguments_use_the_defaults`). `prepare_tools()` also removes the docstring indentation (`inspect.cleandoc`), which was sent to the model as it is and cost about 90 prompt tokens; the wording is not changed. `test_tool_definitions_stay_small` fails if the definitions of all tools grow past 9 300 characters (lowered on 2026-10-20 from 11 400 after merging `create_file` and `get_git_status`, dropping `list_directory` and removing the `context` toolset, from 11 500 on 2026-10-19 after removing the indentation, raised from 11 000 on 2026-10-16 for `suggest_command`, and from 10 500 on 2026-10-01 for `search_relevant_files`, the pointers between the two text searches and `restore_file`).
- Shared code lives in `common.py`, and the parsers and outline functions in `parsing.py`; toolsets never re-implement the path checks, config loading, walking or parsing.
- Built-in generics and `X | None`, double quotes, no bare `except:`.
- Text tools return `Error: <Action> failed:\n{e}\n{traceback}`, except the tools whose responses contain file content (`read_file_with_metadata`, `edit_file`, `web_fetch`), which return `Error (<code>): <message>`; JSON tools always include `"success"` and use `indent=2, ensure_ascii=False`. Error codes are snake_case: a specific condition (`file_not_found`, `hash_mismatch`) or `<action>_error` for an unexpected exception (`read_error`, `search_error`).
- **A failed call says what did not happen.** Small models otherwise assume that a failed edit was partly made, or that the file's hash changed, and read the file again or rebuild it. The message of every refused change of the file tools starts with `Nothing was changed.` (`_not_changed` and `_edit_error` in `filesystem.py`, also `backup_error`), and a failed `edit_file` adds `and expected_sha256 is still valid` once the hash has been checked, so the model can correct `old_text` and retry with the same hash. A refused command starts with `The command was not run.` and a refused suggestion with `The suggestion was not saved.` (`commands.py`). Where it is not certain, the message says so instead: an unexpected exception during a change says that it may have been partly made and names the call that checks it (`_maybe_changed`), and a command that ran and failed or timed out says that a command that changes files may have changed some. Read-only tools do not add it.
- Paths in responses are relative to `project_dir` (`display_path`), as the tools accept and show them elsewhere, so that a small model copies the same form everywhere. Only paths outside it, such as read-only files outside the project, are shown in full.
- Errors and limits say what to do next and name the tool to use, with its arguments filled in where they are known (e.g. `read_file_with_metadata(path='src/app.py', section=...)`).
- Files use CRLF line endings in the working tree (`core.autocrlf=true`); keep them that way when writing files.

## How changes have been verified

The automated test suite in `tests/` (pytest, 349 tests, one to three minutes) covers every toolset. Run it from the repository root:

```bash
python -m pip install -r requirements-dev.txt
python -m pytest tests
```

- `conftest.py` gives every test its own temporary project and tools config (`project` fixture; `make_project` for projects at a specific path, e.g. inside a folder named `out`). `project.load("filesystem")` loads a toolset module fresh for that config, and `start_server()` creates the server with its enabled toolsets in a separate process to test startup errors. The working directory is outside the project, so resolving paths against the working directory instead of `project_dir` fails the tests.
- One test file per toolset (`test_filesystem.py`, `test_outline.py`, `test_search.py`, `test_git.py`, `test_commands.py`, `test_web.py`, which replaces the Ollama client with a fake one, so no requests are sent), plus `test_parsing.py` for the parsers, spans, section names and outline comparison, `test_config.py` for config validation, the disabling settings and the user config file, `test_init.py` for `init` and its templates (the created project starts, the AI can read the instructions and write plans in it, and its `.gitignore` leaves out the right files), `test_protection.py` for the access rules across all toolsets (forbidden, allowed, read-only and protected paths), and `test_servers_start.py`, which starts the server over stdio, also with toolsets and tools disabled and from the repository's own `.mcp.json` and `tools-config.json`, and checks that every toolset defines the tools listed in `TOOLSETS`. It sets `PYTHONPATH` to the repository, so the tests do not need the package installed.
- Windows-only behaviour (name aliases such as `.mcp.json::$DATA`, batch file arguments) is skipped on other systems, and the git tests are skipped if git is not installed.
- The suite was checked by reintroducing earlier bugs (ignored folders compared on the absolute path, protected files not protected, commands run in the working directory); each made tests fail.

Add tests for every new tool or fixed bug.

## Accepted limitations

- The `commands` toolset can reach any file through the code it runs (see the security model).
- In the `git` toolset, a file moved into a forbidden folder is still visible in the history of its old, allowed path, and commit messages are not filtered.
- The `.gitignore` matcher is simplified.
- In a JS/TS file with a syntax error, tree-sitter's error recovery can swallow the declarations after the error, so the outline may be incomplete until the error is fixed. The syntax error itself is always reported.
- `ignored_dirs` names are matched case-sensitively.
- `prepare_tools()` changes the schemas and argument handling, and `__main__.py` takes the tools of the toolsets, through MCPServer's internal `_tool_manager`, as `mcp` has no option for it. An `mcp` upgrade can break it; `test_tool_definitions_stay_small`, `test_null_arguments_use_the_defaults` and `test_server_starts_over_stdio_with_every_tool` then fail.
- The console formatting relies on ollmcp's heuristic for when to render a response as Markdown (see Responses in the console). Another client, or a change in ollmcp, can show the responses differently, but they stay readable as plain text.
- `restore_file` only knows the changes made by the file tools. Changes by commands (e.g. a formatter) or the user are not recorded; a restore over them keeps them in the backup folder, where only the user can get them. Only the last 200 changes are kept.
- `search_relevant_files` does not match word forms: `search` does not find `searching`. Splitting identifiers covers many such cases in code, and stemming would make exact name matches less reliable. Common English words in a query (`the`, `is`) get almost no weight, but words such as `how` can still weigh something in a small project.
- `search_text_in_files` only treats a query as literal text if it is not a valid regex: `func()` is a valid regex that matches `func` without the parentheses, and `a.b` also matches `axb`. The results then include the intended text, with some extra matches.
- Command output is decoded as UTF-8. Python programs are made to write UTF-8 (`PYTHONIOENCODING=utf-8`, found by the test suite), but other programs writing in the Windows code page may still show `�` for characters such as `ä`.

4. **Allow a working folder per command**: an optional `cwd` key in the command registry, relative to `project_dir`, for monorepos.
5. **Find where a name is defined: a `name` parameter for `get_outline`**, e.g. `get_outline(path="", name="validate_order")` → `src/orders/service.py  42-67 validate_order(): Checks the order`. Small models often know a name (from a traceback, a call site or the task) but not its file, and `read_file_with_metadata(path, section=...)` needs the file. `search_text_in_files` finds every use of the name, not only the definition, and a regex covering all JS/TS definition forms (`function x`, `const x = () =>`, class methods and fields, default exports) is too hard for a small model; a folder outline of a large project leaves out nested sections such as methods to fit the output limit. The parameter would outline the files within `path` as now and return only the sections matching `name`, with the matching of section reads (`find_sections` in `parsing.py`, also `Class.method`), each with its file and line span, and the usual limits if many match. A parameter instead of a new `find_definition` tool keeps the tool definitions smaller (about 100 characters instead of 300) and fits the outline → section read workflow. `search_relevant_files` with the name as the query already ranks a section named after it high, which may be enough. Do this after item 2 shows whether models actually get stuck finding definitions.

Also worth considering: a `tools-config.local.json` next to the tools config that overrides single settings and is not committed, for settings that depend on each person's model (`max_output_chars`, `disabled_tools`). And allowing more than one argument in command templates, with numbered placeholders (`{arg1}`, `{arg2}`) checked like `{arg}`, once a real command needs them. A count of arguments was rejected, as an argument string split on spaces breaks expressions such as `pytest -k "total and not slow"`, and small models fill in list parameters less reliably than one string.

## What is deliberately left out

- **Git write tools** (stage, commit, branch): a person reviewing and committing the AI's changes is a sensible safety line.
- **Background processes** (starting a dev server and reading its logs): useful for web apps, but a large addition with its own safety questions. Reconsider if web app development with local models becomes a goal.
- **Environment variable fallback** for the old settings: it would reintroduce the risk of toolsets seeing different settings.
- **Shell features in command templates** (pipes, `&&`, redirection): no safe way to allow them with arguments on Windows. Such logic goes into a script that a template calls.
- **Operating system read-only flags or a `readonly/` subfolder** for read-only files: platform-dependent and easy to lose; `read_only_files` in the config is used instead.
- **An opt-out for `.mcp.json` protection**: not needed, as the user edits the file directly.
- **An `allow_arguments` flag instead of the `{arg}` placeholder**: it could only append the argument to the end, which loses templates such as `ruff check --select={arg} .`, and a misspelled flag would be ignored as silently as a misspelled placeholder. The real problem, a placeholder such as `{args}` passed to the program as literal text, is solved by refusing unknown placeholders at startup.

## Notes for working on this repository

- Environment: Windows, Python 3.14, `mcp` 2.1.1 (`MCPServer`, `Image` from `mcp.server.mcpserver`), `tree-sitter` 0.26.0 with `tree-sitter-javascript` 0.25.0 and `tree-sitter-typescript` 0.23.2, ollmcp 0.35, git 2.54, Ollama 0.40.9 with gemma4:26b (recommended) and qwen3-coder:30b.
- **Read tree-sitter `Point`s by index** (`node.start_point[0]`), never as `.row`/`.column`: attribute access crashes Python 3.14 with an access violation as soon as a file has a few hundred declarations. `test_points_are_read_by_index` guards this.
- The toolsets need `MCP_TOOLS_CONFIG` set when they are imported, also for testing, as `common.py` loads the config on import. When loading toolsets in one test process, remove the package's modules from `sys.modules` before each load so that each gets a fresh config (`parsing.py` reads no config and can stay); the test fixtures in `tests/conftest.py` do this.
- ollmcp passes tool responses to the model as text; `ImageContent` is forwarded only to vision-capable models.
- **The repository path contains `ä`** (in the Windows user name). Tests that read the output of a subprocess set `PYTHONIOENCODING=utf-8` (`test_init.py`), as Python writes to a pipe in the Windows code page otherwise. Terminals may show the character as `�`; check the real text with `ascii()` before concluding that a file is broken.
- **Local AI tests**: the scripts that replay requests against Ollama are in `local_ai_tests/`, which is gitignored and so only in the developer's own copy (see its README and [local_ai_test_results.md](local_ai_test_results.md)). Measure a change to the instructions, the system prompt or the tool definitions with them before keeping it: over several seeds, as single runs vary. `compare_models.py` runs whole tasks (answering, planning, changing a plan, implementing) with checks of the result, for one or more models and with `--instructions` for a draft. The scripts use gemma4:26b by default.
- **`local-only/`** is gitignored too and holds the developer's own material that is not part of the project, such as `presentation.md`, a presentation of the project and its findings, and `broken_output_example.md`, an ollmcp session with broken tool calls (see local_ai_test_results.md).
- **Edit files with scripts saved to files, not shell heredocs**: on this setup, Git Bash heredocs pass non-ASCII characters such as `ä`, and escape sequences such as `\u00e4`, through the shell's encoding and change them. Writing such characters with `chr()` in the script avoids it.
- `pyproject.toml` includes the templates as package data, which a normal (non-editable) install needs for `init`; building a wheel (`python -m pip wheel . --no-deps`) and listing its files checks it.
